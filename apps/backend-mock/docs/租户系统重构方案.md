# 租户系统重构方案

## 1. 背景

现有会员开通链路的隐含模型是：

- 新用户在 `public` 库试用，账号之间互不相关。
- 只有付费后才创建/迁移到独立租户库。
- 迁移对象主要是购买者本人。
- 租户库本身在语义上等同于一个组织，但中心库没有显式组织模型。

新模型需要支持：

- 试用期用户可以先在 `public` 库创建组织。
- 组织创建者是组织内最高权限，但不是 `public` 库的系统 `Super`。
- 组织可以邀请其他用户加入，邀请码能力可以复用，但语义要从“加入租户”扩展为“加入组织”。
- 付费后按整个组织迁移，包括创建者、受邀成员、组织角色、组织内业务数据。
- 也要兼容旧入口：用户直接付费时仍可以填写城市和公司名，此时先创建单人成员组织，再进入同一套 provisioning 流程。

本方案的目标不是一次性重写全部权限系统，而是先补齐可精确匹配和可回滚的基础能力，再逐步把旧的“单用户迁移”收敛成“组织迁移”。

## 2. 设计原则

1. **显式归属优先** 后续迁移不能依赖 `user_id`、`customer_id`、手机号、角色名等间接推断。凡是组织拥有的数据，都应逐步补 `organization_id` 或进入明确的数据归属清单。

2. **权限迁移不参与 OTA** 菜单模板可以 OTA，角色和授权不 OTA。权限只在组织迁移到租户库时生成一次租户权限快照，后续由租户内管理员维护。

3. **菜单是模板，权限是快照** `default` 库作为菜单/code 模板源；`public` 库和租户库菜单/code 可通过 `template_key` 对齐。角色、`role_menu`、`role_code` 是各库内快照，不跟随菜单 OTA 自动重算。

4. **Super 权限只在当前库内生效** `Super` 不是跨库特权。组织所有者在 `public` 库试用阶段不能拥有 public 的 `Super`，避免影响其他试用组织和平台数据；迁移到独立租户库后，可以成为该租户库的 `Super`，拥有该库内的最高权限。

5. **旧租户向前兼容** 已有付费租户要补中心库反向映射，形成 synthetic organization，但不强行改租户库业务数据。

6. **运维动作与代码能力分离** “手动 OTA”指手动触发一套可重复执行的工具，不是把某一次手动同步结果当作代码提交。

## 3. 数据边界

### 3.1 中心库负责的元数据

中心库保存跨库身份、支付、开通和组织映射：

- `organization`
  - `id`
  - `name`
  - `city`
  - `company_short_name`
  - `source_customer_id`：试用期组织通常是 `public`
  - `status`
  - `created_by_center_user_id`

- `organization_member`
  - `organization_id`
  - `center_user_id`
  - `source_customer_id`
  - `source_user_id`
  - `status`
  - `joined_at`

- `organization_invitation`
  - 可以复用现有邀请码生成/核销逻辑，但记录应指向 `organization_id`
  - 邀请时绑定组织角色或组织内默认角色

- `organization_tenant_mapping`
  - `organization_id`
  - `target_customer_id`
  - `target_db_name`
  - `tenant_provisioning_job_id`
  - `status`
  - `legacy`

- `tenant_provisioning_job`
  - 增加 `source_org_id`
  - 逐步弱化 `source_customer_id + initiatorCenterUserId` 作为迁移主体的语义

### 3.2 public/租户库负责的业务数据

业务库仍保存业务表、菜单、角色、用户等本地运行数据。

组织化后，`public` 库会承载多个试用组织，所以 public 内的组织私有数据必须具备可索引的组织归属。不能只靠“创建人是谁”推断，因为受邀成员会共同产生数据。

建议为每类可迁移数据建立一份迁移清单：

| 类型 | 示例 | 迁移谓词 | 必要索引 |
| --- | --- | --- | --- |
| 组织成员 | `user`、员工绑定 | `organization_member` | `(organization_id, center_user_id)` |
| 组织角色 | `role`、`role_menu`、`role_code` | `role.organization_id = ?` | `(organization_id)` |
| 组织业务数据 | 园区、合同、工单等 | 表内 `organization_id = ?` | `(organization_id, id)` |
| 用户私有数据 | 个人配置、草稿 | `center_user_id IN org members` 且业务允许迁移 | 视表而定 |
| 平台数据 | app 版本、系统 key | 不按组织迁移 | 无 |

没有明确归属的表不要进入组织迁移。先补归属字段和索引，再纳入迁移清单。

## 4. 菜单模板体系

### 4.1 字段设计

`menu` 增加：

- `template_key`：跨库稳定身份，唯一。
- `template_parent_key`：父菜单稳定身份，用于 OTA 或复制后重建 `pid`。
- `template_version`：模板版本。
- `template_managed`：是否进入菜单模板体系。
- `template_internal_only`：是否仅供内部库使用；为 `true` 时不发布到 `public` 或租户库。
- `template_deleted_at`：模板下线标记。

`code` 增加：

- `template_key`
- `template_version`
- `template_managed`
- `template_internal_only`
- `template_deleted_at`

`menu_meta` 不需要独立模板键，继续通过 `menu_id` 一对一关联。

字段语义按库分层：

- 在 `default` 模板源库，`template_managed=1` 表示进入菜单模板体系；`template_internal_only=1` 表示仅内部使用，不进入发布候选集。
- 在 `public` 和租户库，`template_managed=1` 表示该记录由上游模板同步创建或维护；它不是发布开关。
- 发布候选集只从 `default` 计算：`template_managed=1 AND template_internal_only=0 AND template_deleted_at IS NULL`。
- 如果一个曾经发布的模板后来在 `default` 被改成 `template_internal_only=1` 或设置了 `template_deleted_at`，OTA 应把目标库中同 `template_key` 且 `template_managed=1` 的记录下线。
- `code.template_internal_only` 通常跟随关联菜单；保留字段是为了支持独立 code 或后续更细粒度过滤。

### 4.2 key 生成规则

不能假设 `auth_code`、`code` 或 `path` 全局唯一。当前 Prisma schema 没有给这些字段唯一约束，真实数据也已经存在重复权限码。

推荐规则：

- 路由菜单优先用 `path` 生成 `menu.template_key`。
- 无 `path` 的权限型菜单使用 `父菜单 template_key + auth_code/name` 定界。
- `code.template_key` 优先跟随关联菜单的 `template_key`，其次再用 `code/name/content`。
- 生成前检查重复 key、孤儿父级、父子成环。

提交 1 的回填脚本只做单库身份回填，不是 OTA：

- 只写 `template_key / template_parent_key / template_version`。
- 不写 `template_managed / template_internal_only`。这些字段属于菜单管理里的发布开关，不能由回填脚本猜测。
- 对 `default`、`public` 和已有租户库运行时都只建立稳定身份，不把任何记录自动纳入模板发布候选集。

### 4.3 模板源与发布流

`default` 是公司内部半开发半生产库，不走会员租户体系，但可以作为菜单模板源。推荐菜单发布流是：

1. 先在 `default` 库修改并验证菜单/code。
2. 确认可发布后，将 `default` 的模板记录 OTA 到 `public` 和各租户库。
3. `public` 不再作为最终模板源，而是 OTA 目标之一。

这样做的好处是内部使用和模板编辑在同一个库完成，避免在 `public` 直接改模板影响试用用户。但必须增加发布边界：

- 只有 `default` 中 `template_managed=1 AND template_internal_only=0 AND template_deleted_at IS NULL` 的菜单/code 才能发布。
- 内部测试菜单、开发工具菜单、公司内部专用视图必须在菜单管理中打开“仅内部使用”开关，即 `template_internal_only=1`。
- 前端菜单管理页需要增加“模板管理”和“仅内部使用”两个开关；“仅内部使用”只对模板管理记录有发布意义。
- 每次发布前必须 dry-run 到 `public`，因为 `public` 是多试用组织共享库，误推影响面最大。
- `default` 自己不参与付费、组织迁移和租户映射，只参与菜单模板发布。

### 4.4 OTA 语义

菜单 OTA 只处理菜单模板：

- `menu`
- `menu_meta`
- `code`

不处理：

- `role`
- `role_menu`
- `role_code`
- `user_role`

OTA 的匹配只基于 `template_key`，不能基于自增 id、名称或路径直接猜。

OTA 推荐分成两阶段：

1. `preflight/dry-run`
   - 枚举目标租户库。
   - 检查 schema 版本、重复 key、缺失 key、孤儿父级、成环。
   - 计算 create/update/disable/parent changed/conflict。
   - 任一租户失败，整批不执行。

2. `execute`
   - 每个租户库单独事务。
   - 先 upsert `menu`，再 upsert `menu_meta/code`。
   - 最后按 `template_parent_key` 修正 `pid`。
   - 目标库下线只影响 `template_managed=1` 且不在当前发布候选集内的同 `template_key` 记录。
   - 每个租户执行后 bump permission cache。

新增菜单默认不要自动授予普通角色，也不需要给 `Super` 写 `role_menu`。现有 `Super` 逻辑按角色名在当前库内直接获得全部启用菜单和更大数据范围；普通角色后续由租户管理员手动分配。

## 5. 权限模型

### 5.1 public 组织权限

public 库需要同时存在平台权限和组织权限：

- 平台 `Super`：管理 public 系统，不属于任何试用组织。
- 组织 owner：管理某个组织，拥有该组织内最高权限，但不拥有 public 库 `Super` 特权。
- 组织成员：通过组织角色获得菜单和 code 权限。

如果继续复用现有 `role` 表，需要给 public 组织角色补组织作用域，例如：

- `role.organization_id`
- `role.scope = system | organization`

public 组织角色树必须按组织隔离：

- 每个组织都有自己的根角色和子角色树。
- 不同组织的 owner 不能共用同一条角色树，即使角色名称相同也必须是不同 `role_id`。
- `role.parent_id` 只能指向同一 `organization_id` 下的角色；不能跨组织挂父子关系。
- `role_menu`、`role_code`、`user_role` 都必须通过角色的 `organization_id` 限制在本组织内。
- 组织 owner 在 public 的菜单管理/角色管理页面只能看到本组织创建的角色和授权，不能看到其他组织的角色、授权或成员。
- public 平台 `Super` 可以看到系统角色和跨组织管理视图，但这属于平台管理，不属于组织 owner 权限。

在未补作用域和查询过滤前，不应允许多个试用组织共享同一套 public 角色记录，否则组织 owner 会在菜单管理中看到外部角色/权限，也会导致后续无法精确迁移组织角色。

### 5.2 迁移到租户库时的权限派生

权限只在 provisioning 时生成租户快照：

1. 读取 `source_org_id` 下的组织成员和组织角色。
2. 在目标租户库创建或复用 `Super` 角色。
3. 组织创建者/owner 映射到目标租户库 `Super`。
4. `Super` 获得该租户库内全部正常管理权限。
5. 普通组织角色按源组织角色树派生到租户库。
6. 保存 `source_role_id -> target_role_id` 映射。
7. 按映射生成 `role_menu / role_code / user_role`。

注意：

- 不能全表复制 public 角色和权限表。
- 不能把 public 系统 `Super` 迁移成租户角色，但可以在目标租户库内授予 owner 该库的 `Super`。
- 菜单/code 可以来自模板源全量复制，但角色授权必须按组织作用域派生。
- 现有代码里的 `Super` 语义本来就是库内最高权限：菜单接口直接返回本库全部启用菜单，园区/租户/考勤/请假/定位/退款/邀请码等接口也按当前库数据范围放大权限。因此组织 owner 迁移到独立租户库后成为该库 `Super` 是合理的，不会跨库影响 public 或其他租户。

## 6. 组织迁移流程

provisioning worker 最终应只认 `source_org_id` 作为迁移主体。

推荐流程：

1. 锁定 `tenant_provisioning_job`。
2. 读取并锁定 `organization`。
3. 校验组织状态、支付状态、目标 customerId/dbName。
4. 创建目标租户库并执行 schema push。
5. 从模板源初始化 `menu/menu_meta/code`。
6. 按 `source_org_id` 迁移组织成员。
7. 迁移组织业务数据。
8. 按组织角色派生租户权限。
9. 写入 `organization_tenant_mapping`。
10. 更新 center user 与 tenant user 绑定。
11. 标记 job completed。

迁移要保存足够的映射：

- `source_center_user_id -> target_user_id`
- `source_org_member_id -> target_user_id`
- `source_role_id -> target_role_id`
- 关键业务表源 id 到目标 id 的映射，按表决定是否持久化。

## 7. 新旧入口兼容

### 7.1 试用期先建组织

1. 用户在 public 创建组织。
2. 创建者成为组织 owner。
3. 组织可生成邀请链接/邀请码。
4. 受邀用户加入同一组织。
5. 付费后 provisioning job 绑定 `source_org_id`。
6. worker 迁移整个组织。

### 7.2 直接付费

旧入口仍允许在购买会员时填写城市和公司名，但内部流程改为：

1. 如果用户没有组织，先创建一个单人成员组织。
2. 用该组织创建 payment/provisioning job。
3. 后续和试用期组织付费走同一条 worker 流程。

这样旧入口不需要长期维护一条“单用户迁移”分支。

### 7.3 已有付费租户

已有租户需要补中心库反向映射：

1. 为每个现有租户创建 synthetic organization。
2. `organization_tenant_mapping` 指向现有 `customerId/dbName`。
3. `legacy=true`。
4. 尽量绑定历史购买者或租户管理员为 organization owner。
5. 不改已有租户库业务数据。

这一步只补中心库元数据，目的是让后续管理、续费、退款、重试、权限说明都能落到同一个组织模型上。

## 8. 提交拆分

### 提交 1：菜单表模板键重构

目标：补跨库稳定身份，不改变现有运行行为。

内容：

- `menu/code` 增加模板字段。
- 当前 API 继续使用 `menuId/pid/codeId`。
- 新增单库 `backfill-keys` 脚本。
- 脚本不标记 `template_managed / template_internal_only`。
- 前端菜单管理暂不需要立即使用新增字段，但后续提交要增加模板管理和仅内部使用开关。

验收：

- 登录、菜单、角色、权限码行为不变。
- Prisma validate 通过。
- 模板源库预览无 duplicate/unresolved；`public` 作为 OTA 目标也要完成预览检查。

### 提交 2：菜单模板发布配置与同步 dry-run

目标：先能配置发布范围，并看清 `default` -> `public/tenant` 差异，不改目标库。

内容：

- 菜单管理页增加“模板管理”和“仅内部使用”开关。
- 后端菜单保存接口支持写入 `template_managed / template_internal_only`。
- `menu_template_sync_job`
- `menu_template_sync_log`
- diff 计算：create/update/disable/parent changed/conflict。
- 支持按单目标库、`public`、全部租户 dry-run。
- diff 的 source publish set 只包含 `default` 中 `template_managed=1 AND template_internal_only=0 AND template_deleted_at IS NULL` 的模板记录。
- 目标库 disable 候选只来自已受模板管理的记录，即目标库 `template_managed=1`。

验收：

- 不写任何租户库业务表。
- 菜单管理页能区分内部菜单和可发布模板。
- 输出每个目标租户的差异和阻断原因。

### 提交 3：菜单 OTA 手动执行能力

目标：提交可重复执行的手动 OTA 工具，不是执行一次同步。

内容：

- 基于提交 2 的 preflight 结果执行。
- 每个租户库单独事务。
- upsert `menu/menu_meta/code` 到 `public` 和目标租户库。
- 修正 `pid`。
- 下线目标库中 `template_managed=1` 且不在当前发布候选集内的记录。
- bump permission cache。

验收：

- 任一租户 preflight 失败时整批不执行。
- 单租户失败可重试。
- 不修改权限表。

### 提交 4：组织基础模型

目标：让 public 试用组织和 legacy tenant 都能被中心库表达。

内容：

- 新增 `organization`。
- 新增 `organization_member`。
- 新增 `organization_invitation` 或扩展现有 invitation 语义。
- 新增 `organization_tenant_mapping`。
- legacy synthetic org 回填脚本。

验收：

- 新老租户都能查到对应 organization。
- 旧付费入口行为不破。

### 提交 5：public 组织权限与迁移权限快照

目标：按 `source_org_id` 派生租户权限。

内容：

- public 组织角色作用域。
- public 组织角色树隔离，菜单管理和角色管理只能操作本组织角色。
- 组织 owner 在 public 阶段是组织内最高权限，迁移到租户库后映射为该库 `Super`。
- `TenantProvisioningJob` 增加 `sourceOrgId`。
- 保存 `source_role_id -> target_role_id`。
- 组织成员 user_role 迁移。

验收：

- public 系统 super 不会进入组织，也不会跨库迁移。
- public 中不同组织 owner 不能互相看到或修改对方的角色树、菜单授权、权限码授权。
- owner 迁移后拥有目标租户库 `Super` 权限。
- 普通成员权限来自组织角色快照。

### 提交 6：统一开通路径

目标：试用期组织付费和直接付费进入同一 provisioning 流程。

内容：

- 试用期已建组织：直接使用已有 `sourceOrgId`。
- 直接付费：先创建单人成员组织。
- 支付回调、重试、退款、开通失败都挂到 organization/job。
- worker 不再以“购买者本人”作为迁移主体。

验收：

- 新旧入口都能开通。
- 重试和退款能按 organization/job 定位。
- 不再新增单用户迁移分支。

## 9. 风险与前置检查

- `public` 库现有业务表如果没有组织归属，不能立即纳入组织迁移。
- 菜单/code 的模板 key 必须先在 `default`、`public` 和已有租户库完成预览检查。
- `template_managed` 不能滥用；只有明确进入模板体系的记录才应标记。
- `template_internal_only` 是发布保护字段；内部菜单必须显式标记，OTA 必须过滤。
- 权限迁移前必须完成 public 组织角色作用域，否则会混入平台角色或其他组织角色。
- provisioning 必须记录映射表或足够日志，否则失败后无法可靠重试。

## 10. 当前阶段结论

第一阶段只做菜单模板身份，不改变权限判断、不改变前端协议、不引入组织迁移主链路。

组织模型、权限派生、整组织数据迁移和统一开通路径分后续提交完成。这样可以先解决跨库精确匹配问题，再逐步收敛会员系统语义。
